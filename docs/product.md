# 서비스 방향 — 우리 모델만 할 수 있는 것

## 1. 근본 주제와 서비스의 연결

프로젝트의 주제는 **승패 예측과 원인 분석**이다. 서비스는 이 두 가지를
그대로 팔아야 한다. 예측만 팔면 "확률 보여주는 사이트"이고, 그건 이미 많다.

**전적 사이트와 우리의 차이는 질문이 다르다는 것이다.**

| | 묻는 질문 | 답하는 방법 |
|---|---|---|
| 기존 전적 사이트 | **무슨 일이 있었나** | KDA · CS · 아이템 — 기록을 보여준다 |
| **우리** | **언제 갈렸나** | 10분 시점 모델로 그 판을 되감아 판정한다 |

10분 시점 모델이 있어야만 나오는 정보가 하나 있다 — **10분의 유불리와
최종 결과를 교차한 판정**이다.

| 10분 | 결과 | 판정 | 이 판에서 진단되는 것 |
|---|---|---|---|
| 유리 | 승 | **굴렸다** | 정상 |
| 불리 | 승 | **역전승** | 후반 집중력 |
| 불리 | 패 | **초반 붕괴** | **라인전 문제** |
| 유리 | 패 | **역전패** | **굴릴 줄 모름 — 복기 1순위** |

같은 패배라도 처방이 정반대다. 초반 붕괴는 라인전을 고쳐야 하고,
역전패는 이긴 판을 닫는 법을 배워야 한다. **기존 전적 사이트는 이 둘을
구분해 주지 못한다** — 10분 시점의 예측이 없기 때문이다.
구현: `src/riot_api.py` 의 `verdict_of()`.

## 2. 타겟 — 누구에게

### 1차: 랭크를 올리려는 개인 유저

- **겪는 문제** — "왜 지는지 모르겠다." 전적 사이트는 KDA 를 보여주지만
  그게 원인인지 결과인지 말해 주지 않는다.
- **우리가 주는 것** — "최근 20판 중 **역전패 6판**. 라인전은 이기는데
  굴리질 못한다." 원인이 어느 쪽인지 가려 준다.
- **왜 우리여야 하나** — 판정에는 10분 시점 승률이 필요하고, 그건 모델이 있어야 나온다.

### 2차: 코치 · 스트리머

- 제자·시청자의 최근 판을 넣으면 **약점 유형이 한 줄로** 나온다.
- 방송에서 "이 사람은 초반형이다" 를 근거와 함께 말할 수 있다.

### 대상이 아닌 것

- **베팅·배당** — 하지 않는다. 분석 도구의 선을 넘지 않는다.
- **실시간 중계 오버레이** — 기술적으로 불가능하다 (4장).
- **아이템·룬 빌드 추천** — 우리 모델이 다루는 정보가 아니다. 하면 열등한 사본이 된다.

## 3. 기능 — 넣은 순서와 넣을 순서

원칙: **모든 기능은 "10분 시점 판정"에서 파생돼야 한다.**
그 뿌리에서 안 나오는 기능은 다른 사이트가 더 잘한다.

| | 기능 | 상태 | 뿌리와의 연결 |
|---|---|---|---|
| F1 | 실제 경기 복기 (시험셋 1,976판) | ✅ | 예측 vs 실제, 틀린 판도 공개 |
| F2 | 구간별 신뢰도 경고 | ✅ | 접전이면 "이 구간 적중률 61.5%" 를 먼저 |
| F3 | 승리요인 기여도 | ✅ | 원인 분석 — 무엇이 그 판을 갈랐나 |
| F4 | 소환사 최근 경기 판정 | ⏸ 키 대기 | **1차 타겟의 핵심 기능** |
| F5 | 판정 요약 타일 (역전패 n판…) | ⏸ 키 대기 | 첫 화면이 진단부터 던진다 |
| F6 | 챔피언별 리드 전환율 | 📋 미착수 | 5장 |
| F7 | 시점별 승률 곡선 (분 단위) | 📋 구상만 | `plan.md` 7장 |

F4·F5 는 서버가 이미 내려준다 (`/api/summoner` 의 `verdict`·`summary`).
**막힌 것은 코드가 아니라 Riot API 키 하나다.**

## 4. 실시간 승률은 왜 못 하나

모델은 10분 시점의 골드·킬·CS 차이를 요구한다. 그런데

- `spectator-v5`(진행 중 경기) → 참가자·챔피언·밴·시작 시각만. **실시간 수치 없음**
- `match-v5` 타임라인 → 그 값들이 있지만 **경기가 끝난 뒤에만** 열림
- Live Client Data API(`127.0.0.1:2999`) → 값은 있지만 **게임이 도는 본인 PC 에서만**

즉 실시간은 웹 서비스가 아니라 **PC 에 설치하는 오버레이**여야 한다.
지금 범위 밖이므로 **끝난 경기 복기**로 선을 그었다.

## 5. 챔피언별 리드 전환율 (F6) — 검토

### 무엇을 만들 것인가

전적 사이트의 챔피언 승률표는 이미 있다. 우리가 더할 것은 **판정을 챔피언별로 쪼개는 것**이다.

> "이 챔피언은 10분 리드를 **굴리는가, 놓치는가**"

| 지표 | 뜻 | 이 챔피언은 |
|---|---|---|
| 리드 전환율 = 굴렸다 / (굴렸다 + 역전패) | 유리하게 시작한 판을 닫는 비율 | 높으면 **스노우볼형** |
| 회복률 = 역전승 / (역전승 + 초반 붕괴) | 불리해도 살아나는 비율 | 높으면 **후반 캐리형** |

챔피언 승률(예: 52%) 하나로는 안 보이는 것이 갈린다 — 같은 52% 라도
"초반에 벌어 끝내는 챔피언"과 "초반을 버티고 뒤집는 챔피언"은 완전히 다르다.
**이건 10분 시점 판정이 있어야만 계산된다.**

### 데이터 — 그마~챌린저 수집

현재 데이터셋(Kaggle 다이아 10분 스냅샷)에는 **챔피언 컬럼이 아예 없다.**
따라서 Riot API 로 새로 모아야 한다.

```
league-v4 (challenger/GM/master 엔트리)  →  puuid 수천 개
  → match-v5 match ids (큐 420 솔로랭크)
    → match 상세      : championName · teamPosition · win     (1 요청)
    → match timeline  : 10분 시점 13개 지표                    (1 요청, 응답이 크다)
```

**비용 추정** (개발용 키 기준: 100요청 / 2분)

| 목표 | 요청 수 | 예상 시간 |
|---|---|---|
| 챔피언×라인 승률만 (타임라인 불필요) | 약 5,500 | 약 2시간 |
| **판정까지 (타임라인 필요)** | 약 10,500 | **약 3.5~4시간** |

### 결정하기 전에 알아야 할 것 3가지

1. **개발용 키는 24시간마다 죽는다.** 4시간짜리 수집이 중간에 끊기므로
   **이어서 받는(resumable) 수집기**가 필수다. 받은 것을 즉시 파일에 append 하고,
   이미 받은 match id 는 건너뛰는 구조여야 한다.
2. **모델을 다시 학습하는 게 아니다.** 챔피언을 피처로 넣자는 것이 아니라,
   기존 모델의 판정을 챔피언별로 **집계**하는 것이다. 그래서 `artifacts/` 는 그대로다.
   (챔피언은 0분 정보라 10분 모델의 피처로는 적합하지 않다 — `plan.md` 7-2 참고)
3. **티어가 바뀌면 분포가 바뀐다.** 그마~챌 표본으로 만든 값을
   다이아 이하 유저에게 그대로 보여주면 안 된다. **"그마~챌 기준"** 을 화면에 명시해야 한다.

### 우선순위

F6 은 **F4·F5 다음**이다. 둘 다 같은 키를 기다리는데, F4·F5 는 이미 서버가
계산까지 끝냈고 F6 은 수집기부터 새로 짜야 한다. 키가 살아나면
**F4·F5 를 먼저 눈으로 확인하고**, 그다음 수집을 건다.
