## R2. 시점 인자 구조 (FR-009 · SC-009)

> **9/1 갱신 주석** — 아래 R2 절의 '대안 1·2'는 Vue/Express 스택을 전제로 한 8/31 검토 기록이다. 실제로는 **Flask 단일 스택**을 택해 두 대안이 모두 불필요해졌다 — 웹이 같은 프로세스에서 `predict.py` 를 import 하므로 예측 경로가 하나이고, 파리티는 `web/test_parity.py` 로 기계 검증한다.


**결정** — 시점을 **데이터 소스 선택과 피처 정의를 함께 결정하는 단일 인자**로 만든다.

```
SNAPSHOT_MINUTE (기본 10)
  → SNAPSHOT_SOURCES[minute]  = 테이블명 / CSV 경로
  → DIFF_SPEC[minute]         = R1의 유도 규칙 (10분은 위 13개)
  → artifacts/<minute>min/    = model.joblib · schema.json · model_params.json · 리포트
```

`train.py --minute 15` 로 실행하면 **예측 로직을 한 줄도 고치지 않고** 같은 절차가 돈다.
데이터가 없으면 소스 조회 단계에서 `SnapshotUnavailableError` 로 **사유를 지목해 중단**한다(AS8).

**근거** — FR-009의 완료 조건은 "15분 확보 시 절차 수정 없이 재실행 가능함을 확인"까지다.
산출물 경로를 시점별로 분리해 두면 나중에 두 시점 결과가 같은 저장소에 공존할 수 있어,
후속 과제(FR-007 표본 통제)가 재작업 없이 이어붙는다.

**대안** — 시점을 파일명 접두어로만 쓰기. 피처 정의가 시점에 묶이지 않아 15분에서
"10분에만 존재하는 파생"이 새어들 수 있다. 원리 2 위반 소지로 배제.

**검증** — 데이터 없이도 확인 가능한 회귀 테스트를 둔다: `--minute 15` 실행이
**전처리·학습 코드를 타기 전에** 명확한 미확보 오류로 끝나는지, 그리고 `--minute 10` 과
분기하는 코드가 `config` 한 곳뿐인지(다른 모듈에 `10` 리터럴 0건) 검사한다.

## R3. 웹 계층의 확률 재현 방식 (NFR-008 · A12 · FR-019)

**결정(8/31)** — 학습이 `artifacts/10min/model_params.json` **하나**를 내보내고, 서버는 그 수치로
로지스틱 산술만 옮긴다. JS 쪽에 임계값·계수·구간을 **손으로 적지 않는다**.

```
p(win) = sigmoid( intercept + Σ coef[i] × (x[i] − mean[i]) / scale[i] )
```

`model_params.json` 은 계수·절편·정규화 통계·지표 순서에 더해 **화면이 필요로 하는 나머지 전부**
— 공통 상위 요인 목록(FR-007 산출물), 경고 임계값과 구간별 실측 정확도(FR-006) — 를 함께 담는다.
그래야 SC-015("근거 목록이 `predict.py` 반환값과 동일")가 **우연이 아니라 구조적으로** 성립한다.

**근거** — A12가 웹 계층의 역할을 "파라미터 수치 재현"으로 한정했고, 정당성은 전건 일치
검증으로만 확보된다고 못박았다. 표시 계층이 자체 상수를 갖는 순간 원리 7 위반이다.

**대안 1** — Express 가 `predict.py` 를 `child_process` 로 호출. 예측 경로가 하나로 유지되어
파리티 문제가 원천 소멸하지만, A12가 지정한 방식이 아니고 요청마다 인터프리터 기동 비용이
붙어 NFR-007(체감 지연 없음)에 불리하다. 배제하되 **파리티 실패 시 폴백 후보**로 기록.

**대안 2** — Python 예측 서버(FastAPI 등)를 따로 띄우고 Express 가 프록시. 실행 계층이 하나
더 늘어 A13(네이티브·추가 계층 없음) 취지에 어긋난다. 배제.

## R4. 서빙 파리티 검증의 실행 형태 (FR-019 · SC-016)

**결정** — 서버를 띄우지 않고 돌아가는 **오프라인 전건 대조**를 1차로 삼는다.

1. `ml/parity.py` 가 홀드아웃 전량(약 1,976행)을 `predict.py` 로 통과시켜 확률 벡터를 만든다.
2. 같은 입력을 `node backend/src/parity-run.js` 에 넘긴다 — 이 스크립트는 Express 라우트가
   쓰는 **바로 그 `predictor.js` 모듈**을 호출한다.
3. 최대 절대 오차 ≤ `1e-9` 전건 확인. 1건이라도 벗어나면 **종료 코드 1** 로 배포를 막는다.
4. 결과를 `artifacts/10min/parity_report.json`(대조 건수·최대 오차·합격 여부·검증 일시)으로 남긴다.

추가로 서버 기동 상태에서 **HTTP 경로 표본 대조**(예: 20건)를 붙여, 라우트의 직렬화·파싱이
값을 바꾸지 않음까지 확인한다. 전건을 HTTP 로 돌리지 않는 이유는 CI 없이 로컬에서 반복
실행할 절차이기 때문이다(NFR-005 경량 실행).

**부동소수 관점** — Python 과 JS 모두 IEEE754 배정밀도이고 연산이 곱·합·`exp` 뿐이라
누적 오차는 1e-15 수준이다. `1e-9` 는 충분히 여유 있는 관문이다. 단 **연산 순서를 지표
순서로 고정**해 재현성을 확보한다.

**대안** — 웹 계층에서 나온 확률을 반올림해 비교. E11이 금지한 "판단값 변형"에 해당한다. 배제.

## R5. 경고 산출 규칙 (FR-006 · SC-006)

**결정** — 경고는 두 종류이며 **모두 학습 산출물에서 나온다**. 거부와는 반환 경로가 다르다.

| 유형 | 발동 조건 | 동봉 정보 | 출처 |
|---|---|---|---|
| `out_of_range` | 어떤 지표가 `schema.json` 의 `[min, max]` 밖 | 해당 지표명, 입력값, 학습 관측 범위 | 학습 시 관측 최소·최대 |
| `close_game` | `abs(goldDiff) ≤ 1000` | 해당 구간 실측 정확도, 구간 표본 비율 | 오류 리포트의 구간 집계 |

`close_game` 의 임계 1,000과 정확도는 **명세 A3의 실측값을 코드에 적는 것이 아니라**,
`evaluate.py` 가 산출한 구간 집계를 `model_params.json` 으로 흘려보내 읽는다. 수치가 바뀌면
문서·화면·응답이 함께 바뀐다(원리 7).

**거부(경고 아님)** — 컬럼 누락 · 이름 불일치 · 자료형 불일치. `schema.json` 대조로 판정하고
예외를 던진다. AS3가 요구한 "경고 / 거부" 이분법을 응답 계약 수준에서 분리한다.

## R6. 근거 지표 산출 — 두 방법 교차 (FR-007 · SC-003)

**결정** — ① 표준화 계수(방향 + 크기) ② 순열 중요도(기여도)를 각각 산출하고,
**양쪽 상위 8개에 공통 등장한 지표만** 응답의 근거로 노출한다. 순열 중요도는
`n_repeats=30`, seed 고정으로 산출해 변동을 억제한다.

방향(+/−)은 **계수 부호에서만** 가져온다 — 순열 중요도는 크기만 주고 방향을 주지 않기 때문이다.
공통 요인이 5개 미만이면 학습을 실패로 처리한다(SC-003이 성공 기준이므로 조용히 넘길 수 없다).

**근거** — 29피처 실측에서 상위 8개 중 6개가 공통이었고(measured-facts §6), 차이 지표 구성에서
7개로 는다는 것이 A1의 채택 근거 중 하나다. R1의 증거 공백과 함께 재확인 대상이다.

**개별 예측의 기여도** — 응답의 근거는 전역 순위(위)를 그 경기의 표준화 입력값으로 부호를
맞춘 값으로 제시한다: `contribution[i] = coef[i] × z[i]`. 로지스틱에서 이 값은 로그오즈 기여
그 자체라 **추가 근사 없이** 방향과 크기를 동시에 준다(원리 4). SHAP 등 별도 설명기를 얹지 않는다.

## R7. 경기 유형 자동 분류 (FR-020 · SC-017 · A14)

**결정** — 진영 식별 정보를 배제한 **사이드 중립 지표 4개**로 KMeans 분류한다.

| 중립 지표 | 정의 |
|---|---|
| `absGoldDiff` | `abs(goldDiff)` — 격차의 크기(방향 제거) |
| `absExperienceDiff` | `abs(experienceDiff)` |
| `totalKills` | `blueKills + redKills` — 교전 총량 |
| `totalObjectives` | 양 팀 드래곤 + 전령 + 타워 합 |

`k ∈ {2, 3, 4}` 를 실루엣 계수로 선택하고 seed 를 고정한다. 유형별로 **경기 수**와
**10분 리드팀의 최종 승률**(`sign(goldDiff)` 가 승자와 일치한 비율)을 산출한다.

**진영 정보 배제의 구조적 보장** — 분류 입력에 부호가 있는 지표를 넣지 않는다. 코드 상수를
`SIDE_NEUTRAL_FEATURES` 로 분리하고, 테스트에서 **블루/레드를 통째로 뒤집은 데이터로 다시
분류했을 때 같은 배정이 나오는지** 검사한다. AS14의 "진영 정보 미포함"을 눈으로 확인하는
대신 **불변성 테스트로 강제**한다(원리 2와 같은 방식).

**A14 해소** — 외부 세션 산출물의 반입을 기다리지 않고 **최종 노트북 안에서 재산출**하는
경로를 택한다. A14가 둘 중 하나를 완료 조건으로 인정했고, 재산출이 재현성(NFR-001)과
클린 실행(NFR-006)에 모두 유리하기 때문이다.

**대안** — `abs(goldDiff)` 구간을 손으로 나눈 규칙 분류. 해석은 쉬우나 001-FR-016이 "자동
분류"를 요구하고, 규칙 임계값을 사람이 정하는 순간 원리 7의 경계에 닿는다. 실루엣 선택
결과의 **타당성 점검용 대조군**으로만 쓴다.

**결정** — 원천 테이블을 직접 읽지 않고 **DB View 를 통해서만** 읽는다.
피처 정의가 SQL 한 곳에 있어, Python·Node·노트북이 같은 정의를 공유한다.

| 피처 | `v_lol_10min_diff13`(16) · `clean29`(31) · `simple2`(4) · `neutral`(15) | 학습 입력 · 대조군 · 간편 입력 · 경기 유형 |

**분할은 `ml_split` 테이블로 고정되어 있다**(train 7,903 / test 1,976, 층화 seed 42).
`dataset.py` 는 다시 뽑지 않고 읽는다 — "우연히 좋은 분할"을 배제한다(원리 5).

`ml/dataset.py` 는 View 를 조회하고 결과를 `data/`(gitignore 대상)에 CSV 로 캐시한다.
접속 정보는 `.env` → 환경 변수로만 주입하며, 기존 `scripts/_db.js` 규약을 Python 쪽에서도
동일하게 맞춰 README 한 줄로 설명되게 한다.

**View 를 쓰는 이유는 편의가 아니다** — 차이 지표 정의가 Python 코드에만 있으면
노트북·검증 스크립트·후속 세션이 각자 다시 계산하게 되고, 그 순간 정의가 갈라진다.

**대안 1** — 원천 테이블을 읽고 Python 에서 차이 지표 생성. 정의가 코드에 갇혀 위와 같은
분기 위험이 생긴다. 배제.
**대안 2** — CSV 를 저장소에 커밋. 라이선스·용량·NFR-009 위반. 배제.

**검증** — `node scripts/create-views.js` 가 51항목을 확인한다: 컬럼명·순서 계약 일치,
중복·파생 컬럼 0건, 진영 편향 컬럼 0건, NULL 0건, `gameId` 전수 유니크, 타깃 균형,
항등식 5건 전수 대조, 진영 불변성(blue/red 뒤집기), 분할 겹침 0건, long 행수 = 경기 × 14,
요인 순위가 train/test 에서 뒤집히지 않음, 격차 구간별 리드팀 승률의 단조 증가.
멱등이므로 CI 없이도 반복 실행할 수 있다.

## R13. 외부 유사 승패 판별 모델 대조 (v1.1 · 사용자 요구 2)

**결정** — 외부 결과를 **성능 목표의 근거가 아니라 천장의 검증**으로 인용한다.
인용 시 **① 관측 시점 ② 모집단 티어 ③ 분할 방식**을 반드시 병기한다.

| 출처 | 시점 | 최고 모델 | 정확도 |
|---|---|---|---|
| 본 프로젝트 | 10분 | 로지스틱 (diff13) | 0.7136 (`ml_split`) · CV 0.730~0.737 |
| Kaggle 공개 커널 (동일 형태 데이터 9,879×40) | 10분 | 로지스틱 | ~0.73 |
| 〃 | 10분 | XGBoost / RF | ~0.72 |
| Lafrance & Grewal 2026 (20,781경기) | 10분 | XGBoost | 0.727 (전 모델 0.719~0.727) |
| arXiv 2309.02449 | 진행 60~80% | LightGBM | 0.8162 |
| MOBA 앙상블 연구 다수 | 경기 전체/후반 | LightGBM·하이브리드 | 0.95~0.98 |

**Rationale**
1. **천장은 데이터의 성질이다** — 독립 수집 데이터(20,781경기)에서도 10분 시점 상한이 0.727 이다.
   우리 0.71~0.73 이 같은 대역이므로, 001 A5 의 "0.75 도달 곤란"이 외부로 확증된다.
2. **XGBoost 도 로지스틱을 못 이긴다** — 10분 시점에서 두 모델 차이가 오차 범위다.
   `bakeoff.py` 의 결론(로지스틱 1위)과 방향이 같아, 원리 4 채택이 성능 희생이 아님을 방어할 수 있다.
3. **0.95+ 는 비교 대상이 아니다** — 전부 후반/전체 경기 데이터다. 시점이 다르면 비교가 아니라 참고다(원리 3).
4. **모집단이 다이아~마스터 솔로큐다** — 우리 원천의 행 수·컬럼 수가 공개 Kaggle 데이터셋과 일치한다.
   001 이 확장 데이터를 "프로 경기"로 적어 둔 것과 다르므로, **후속 15분 비교는 같은 티어로 맞춰야 한다.**

**Alternatives considered** — 외부 최고 수치(0.98)를 목표로 상향: 원리 3 위반이라 기각.
외부 비교 생략: 사용자 요구 2 이며, 무엇보다 "0.71 이 낮은 점수인가"라는 질문에 답할 근거가 사라진다.

**적용 위치** — `docs/model_card.md` 의 "성능"·"한계"·"사용 금지 상황" 세 절. M7 이 저장소 안 재현을 담당한다.

**Alternatives considered** — 모델을 M1 하나로 유지하고 나머지는 노트북에 두는 안:
사용자 요구 1("기능으로 구성")과 정면으로 어긋나고, 노트북 재실행마다 수치가 흔들리는 문제가 남는다.
