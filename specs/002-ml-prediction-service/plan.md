# 어떻게 만들었나 (plan)

4일 계획과 실제 결과. 팀원 누구나 읽을 수 있게 간결하게 정리한 판이다.

## 4일 동안 한 일

| 날 | 한 일 | 그날의 결과물 |
|---|---|---|
| Day 1 | 데이터 확인 → 연습/시험 나누고 시험지 봉인 → 찍기 점수 재기 | 찍기 0.5009 (모든 비교의 출발선) |
| Day 2 | 중복 컬럼 11개 정리 → "파랑−빨강" 차이값 13개로 압축 → 경기 유형 묶기 | 피처 확정 (점수 0.7334 → 0.7369) |
| Day 3 | 모델 8종 비교 → 로지스틱 회귀 확정 → 5조각 교차검증 | 모델 확정 (1등 + 안 외움 + 설명 가능) |

| 추가 | 10분 vs 15분 실험 · 10번 반복 검증 · 웹 화면 | +5.25%p (팽팽한 경기만) |

## 무엇으로 만들었나

| 부분 | 도구 | 왜 |
|---|---|---|
| 학습·예측 | Python + scikit-learn | 수업에서 배운 범위 |
| 모델 | 로지스틱 회귀 | 점수 1등 + 이유를 숫자로 설명 가능 |
| 데이터 보관 | 팀 MariaDB (계산식은 DB 쪽에) | 누가 읽어도 같은 13개가 나오게 |
| 웹 화면 | Flask | 아래 참고 — 계획에서 바뀐 것 |
| 모델 저장 | joblib 파일 하나 | 전처리까지 통째로, 복원 검증 |

**계획에서 바뀐 것 — 화면을 Vue/Express 대신 Flask로.**
원래 계획은 예측 계산이 파이썬과 자바스크립트 두 군데에 생기는 구조였다.
그러면 화면 확률과 모델 확률이 달라져도 아무도 모른다. 이게 이 설계의 최대 위험이었다.
Flask는 화면도 파이썬이라 예측 파일을 그대로 불러 쓴다. 계산이 한 곳뿐이라 어긋날 수 없다.

## 지킨 원칙 7가지

1. 나누는 게 먼저 — 시험지를 봉인한 뒤에 전처리한다 (반대로 하면 점수가 가짜로 오른다)
2. 찍기 점수를 먼저 잰다 — 그래야 "잘했다"를 말할 수 있다
3. 전처리는 모델과 한 덩어리로 묶는다 — 검증 중에도 시험 정보가 안 새게
4. 연습 점수와 검증 점수를 나란히 본다 — 외웠는지 확인
5. 비교할 땐 하나만 바꾼다 — 시점 비교에서 시점 말고 전부 고정
6. 한 번의 점수를 믿지 않는다 — 5조각 검증 + 10번 반복
7. 사람 지식은 재료 고를 때만 — 예측 규칙으로는 넣지 않는다
